# Commit

변경사항을 분석하여 컨벤션에 맞게 커밋하는 스킬이다. 사용자 승인을 따로 받지 않고 바로 커밋한다.

## 절차

### 1. 변경사항 분석

다음을 실행해 현재 상태를 파악한다.

```bash
git status --short
git diff            # 아직 stage하지 않은 변경
git diff --staged   # 이미 stage된 변경
git log --oneline -10   # 기존 커밋 메시지 스타일 확인
```

- git 저장소가 아니면 커밋하지 말고 사용자에게 알린다.
- 변경이 없으면 "커밋할 변경사항이 없어요"라고 알리고 끝낸다.
- 새 파일(untracked)도 내용을 읽어 목적을 파악한다.
- `.env`, 키·토큰이 들어간 파일, `node_modules`, 빌드 산출물은 커밋 대상에서 제외하고 사용자에게 알린다.

### 2. 논리적 단위로 분류

- 하나의 커밋은 하나의 목적만 담는다. 서로 다른 목적(기능 추가 + 설정 변경 등)이 섞여 있으면 나눈다.
- 파일 단위로 나누기 어려우면 `git add -p`는 대화형이라 쓸 수 없으므로, 나누지 않고 하나로 묶되 이유를 설명한다.
- 테스트는 대상 코드와 같은 커밋에 둔다.
- 커밋 순서도 정한다. 앞 커밋만으로 빌드가 깨지지 않게 한다.

### 3. 한국어 커밋 메시지 작성

형식:

```
<type>: <요약>

<본문 (선택)>
```

| type | 용도 |
| --- | --- |
| feat | 새 기능 추가 |
| fix | 버그 수정 |
| refactor | 동작 변경 없는 구조 개선 |
| chore | 설정, 의존성, 빌드, 문서 등 기타 |

작성 규칙:
- 요약은 한국어로, 50자 안팎, 마침표 없이 쓴다. 무엇을 했는지 구체적으로 적는다.
  - 좋음: `feat: MZ 스타일 스티커 UI 테마 적용`
  - 나쁨: `fix: 수정`, `chore: 업데이트`
- 이유(왜)가 코드만으로 드러나지 않을 때만 본문을 쓴다. 본문은 한 줄 비우고 시작한다.
- 위 4개 외의 type은 쓰지 않는다. 테스트 추가는 대상에 따라 feat/fix에 포함하거나 chore로 쓴다.
- 메시지 마지막에 시스템 지침이 정한 공동 작성자 줄이 있으면 빈 줄 뒤에 붙인다.

### 4. 바로 커밋

1. 승인을 기다리지 않고 분류한 커밋 단위대로 바로 커밋한다.
2. 커밋 단위마다 해당 파일만 이름으로 stage하고 커밋한다. `git add -A`와 `git add .`는 쓰지 않는다.

   ```bash
   git add <파일들>
   git commit -m "$(cat <<'EOF'
   feat: 요약

   본문

   Co-Authored-By: ...
   EOF
   )"
   ```

3. 모든 커밋이 끝나면 `git log --oneline -n <커밋 수>`와 `git status --short`로 결과를 확인하고, 만든 커밋 목록과 제외한 파일(이유 포함)을 사용자에게 보고한다.

## 금지 사항

- `git push`는 사용자가 따로 요청하기 전에는 하지 않는다.
- `--no-verify`, `--amend`, `git reset --hard` 등은 사용자가 명시적으로 요청하지 않는 한 쓰지 않는다.
- pre-commit 훅이 실패하면 원인을 고치고 새 커밋으로 다시 시도한다.
