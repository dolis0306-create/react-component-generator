# TDD Rule

> **경고: 이 규칙은 Rigid다. 상황에 맞게 변형하지 마라. 적힌 그대로 따른다.**

## 프로젝트별 규칙 우선

- 프로젝트의 `CLAUDE.md` / `AGENTS.md`에 TDD 규칙이 있으면 **그것이 우선**한다.
- 이 파일은 **기본값(fallback)** 이다. 프로젝트 규칙과 충돌하지 않는 부분에만 적용한다.

## 1. 적용 기준

### TDD 필수

- **비즈니스 로직**
- **API** (핸들러, 요청/응답 처리)
- **유틸 / 순수 함수**
- **버그 수정** (버그를 재현하는 실패 테스트를 먼저 작성)

### TDD 불필요

- 타입 정의
- 설정 파일
- 순수 UI (로직 없는 마크업/스타일)
- SQL

판단이 애매하면 **TDD를 적용한다.**

## 2. RED-GREEN-REFACTOR

### RED

- **하나의 동작 = 하나의 테스트.** 여러 동작을 한 테스트에 묶지 않는다.
- 테스트를 **반드시 실행해서 실패를 확인**한다. 실행하지 않은 RED는 RED가 아니다.
- 실패 이유가 **"기능 미구현"** 이어야 한다. 문법 오류, import 오류, 잘못된 셋업으로 인한 실패는 RED로 인정하지 않고 테스트를 고친다.

### GREEN

- 테스트를 통과시키는 **최소한의 코드만** 작성한다.
- **YAGNI.** 아직 테스트가 요구하지 않는 기능, 분기, 옵션을 추가하지 않는다.
- **신규 테스트와 기존 테스트 모두** 실행해 통과를 확인한다.

### REFACTOR

- 중복 제거, 이름 개선, 헬퍼 추출만 한다.
- **green을 유지**한다. 변경할 때마다 테스트를 실행한다.
- **새 동작을 추가하지 않는다.** 새 동작은 다음 RED에서 시작한다.

### 반복

- 다음 동작에 대한 **RED로 돌아간다.** 모든 요구 동작이 끝날 때까지 반복한다.

## 3. 삭제 강제

- 테스트보다 **프로덕션 코드를 먼저 작성했다면 삭제하고 RED부터 재시작**한다.
- **"참고용"으로 남기는 것도 금지**한다. 보면서 다시 쓰는 것은 삭제가 아니다.

## 4. 변명 차단표

| 변명 | 반론 |
|------|------|
| 너무 단순해서 테스트 불필요 | 단순한 코드가 가장 쉽게 깨지고, 테스트도 가장 빨리 쓴다. 단순하면 비용이 거의 없다. |
| 나중에 추가하겠다 | 나중에 쓴 테스트는 구현에 맞춰져 즉시 통과하고 아무것도 증명하지 못한다. 나중은 오지 않는다. |
| 시간이 없다 | 실패 테스트 없는 수정은 디버깅 시간으로 돌아온다. TDD가 더 빠른 경로다. |
| 삭제하면 낭비다 | 이미 쓴 코드는 매몰 비용이다. 검증되지 않은 코드를 유지하는 쪽이 더 큰 낭비다. |
| 프로토타입이다 | 프로토타입은 그대로 프로덕션이 된다. 버릴 코드라면 더더욱 삭제 비용이 없다. |
